## Confirmed capacity regression

The reproduction uses one admitted session and 65 distinct original call IDs.
The first 64 calls are Read with uncertainty 0.9; all have matching authoritative
Ask evidence and `policy_unconfirmed_ask` client refusals, with ledger count zero.
Call `sou17-benign-after-asks` changes only the synthetic score to uncertainty 0.05;
its classifier record says authoritative Allow. The collector then returns EOF,
exits 1 and logs `MCP admission request rejected`. The fixture ledger remains
empty; there is no original server result for that call. Native audit contains
64 Allow call receipts and no result receipts.

Source explains the capacity mechanism: the collector requests a native receipt
before applying the authoritative refusal
([admission.rs:1476–1492](https://github.com/SoupTeam/soup-wall/blob/b76910a5ec98d740e7c78541a9876ab11ddb272b/crates/agentfw/src/mcp/admission.rs#L1476)).
The daemon stores each uncompleted permit under its 64-call session cap
([native.rs:746–801](https://github.com/SoupTeam/soup-wall/blob/b76910a5ec98d740e7c78541a9876ab11ddb272b/crates/agentfw/src/native.rs#L746)).
The rejected HTTP response body is discarded, so `native_call_cap` is a
code-supported explanation, not a directly observed error code in this evidence.
Impact: a sequence of correctly refused requests interrupts useful work in the
same session. Coordinate the production fix through Nari_Ab/SOU-15; the fix must
retain native hard-deny precedence and pass this regression.
